# Gigflow: working agreement for Claude Code sessions

Two people build this app, each with their own Claude Code. Both sessions read this file, so it is the single source of truth for how work happens here. Keep it short and keep it current.

## Project facts

- TanStack Start (React 19) + TypeScript, Tailwind 4, shadcn/ui (`src/components/ui`, style "new-york"), TanStack Query, Supabase JS. Built by Vite + Nitro to a Cloudflare Worker in `.output/`.
- Origin: a Lovable export (2026-10-21). Not synced with Lovable anymore; this repo is canonical. `@lovable.dev/vite-tanstack-config` still provides the Vite config; do not add tanstackStart/react/tailwind plugins manually (see comment in `vite.config.ts`).
- Node 22 (`.nvmrc`), npm, commit `package-lock.json`. No bun.
- `.env` is gitignored. Copy `.env.example` and fill in the Supabase publishable values. Never commit a service-role or `sb_secret_` key anywhere.
- `npm run lint` (ESLint + Prettier), `npx tsc --noEmit -p tsconfig.json`, and `npm run build` must pass before a PR is opened. Run `npm run format` to fix formatting.
- Routes are file-based under `src/routes/`; `src/routeTree.gen.ts` is generated by the router plugin on dev/build and is committed. Do not hand-edit it.
- Files in `src/integrations/supabase/` marked "automatically generated" came from Lovable; edit with care and say so in the PR.

## Workflow (non-negotiable)

1. **Never commit directly to `main`.** It is protected. All work goes through a pull request.
2. **One issue, one branch, one PR.** Branch names: `feat/<short-name>`, `fix/<short-name>`, `chore/<short-name>`. Reference the issue in the PR body (`Closes #12`).
3. **Claim before you build.** Assign yourself to the GitHub issue (or comment "taking this") so two people do not build the same thing.
4. **Small PRs.** Prefer several focused PRs over one large one.
5. **Pull `main` before branching** and merge `main` into your branch before asking for review.
6. **Merging:** the author merges after CI is green and the other collaborator has had a look (or has said "go ahead" on the PR). Use "Squash and merge".

## Code conventions

- Function components with hooks. Server-only code goes in `*.functions.ts` (server functions) or `src/routes/api/`; never import `client.server.ts` from client code.
- TypeScript strict stays on, including `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes`. No `any` without a comment.
- Tailwind utility classes; shared design tokens live in `src/styles.css`. Add shadcn components with the CLI (`npx shadcn@latest add <name>`), not by hand.
- Data access goes through `src/lib/gigflow.ts` / `src/lib/data.ts`, not ad-hoc Supabase calls in components.
- Add a dependency only when it earns its place, and say why in the PR.

## Commit messages

Conventional-style, imperative, short subject line: `feat: add gig list view`, `fix: prevent duplicate gigs on refresh`, `chore: bump vite`, `docs: describe deploy flow`.

## Where things live

- Hosting and deploy: `docs/HOSTING.md`.
- Contributor onboarding: `docs/COLLABORATOR-SETUP.md`.

## For Claude specifically

- Before starting a task, run `git fetch && git status` and make sure you are on a fresh branch off `origin/main`.
- Before opening a PR, run lint, tsc, and build and include the result in the PR body.
- Do not edit `.github/workflows/*`, `vite.config.ts`, or `src/start.ts` without flagging it in the PR title.
- If you are unsure whether something is in scope, open an issue and ask instead of building it.
